## 1. System Overview

This repository implements a **GPS-denied navigation stack** for VTOL UAVs using onboard visual-inertial odometry and SLAM.

| Layer           | Technology                                              |
| --------------- | ------------------------------------------------------- |
| OS              | Ubuntu 22.04 LTS / Raspberry Pi OS (ARM64)              |
| Middleware      | ROS 2 Humble Hawksbill                                  |
| Flight stack    | PX4 Autopilot v1.14+                                    |
| Bridge          | `px4_ros_com` + `px4_msgs` (uXRCE-DDS / MicroXRCE-Agent) |
| Perception      | `quadcopter_perception` (YOLOv8 semantic segmentation)  |
| Autonomy        | `quadcopter_bringup` (planning, VIO, SLAM nodes)        |
| Sensors         | SC132GS Binocular Stereo Camera, IMU (on FC)            |
| Compute         | Raspberry Pi 5 (8GB)                                    |
| Simulation      | Gazebo Ignition (SITL)                                  |

The companion computer (Raspberry Pi 5) talks to the Kakute H7 flight controller over UART through the MicroXRCE-DDS agent; PX4 uORB topics are exposed on the ROS 2 graph via `px4_msgs`.

## 2. Prerequisites

### 2.1 Host Requirements

- **Ubuntu 22.04 LTS (jammy)**, 64-bit (ARM64 for Raspberry Pi 5).
- **ROS 2 Humble** (desktop or ros-base).
- Python 3.10+, `colcon`, `rosdep`.

### 2.2 Install ROS 2 Humble

Follow the official [ROS 2 Humble installation guide](https://docs.ros.org/en/humble/Installation.html).
Then install the build toolchain:

```bash
sudo apt install -y python3-colcon-common-extensions python3-rosdep
sudo rosdep init
rosdep update
```

### 2.3 Optional / Peripheral Tools

| Tool               | Purpose                              | Install                                    |
| ------------------ | ------------------------------------ | ------------------------------------------ |
| PX4 Autopilot      | Firmware (SITL or hardware flashing) | [PX4 Dev Guide](https://docs.px4.io/main/en/dev_setup/building_px4.html) |

| MicroXRCE-Agent    | uXRCE-DDS agent (companion side)     | `sudo apt install ros-humble-micro-ros-agent` or build from source |
| QGroundControl     | Ground control station               | [QGC Downloads](https://qgroundcontrol.com/downloads/) |
| Git LFS            | Large binaries / logs                | `sudo apt install git-lfs`                 |


```bash

```

### 5.1 Selective Builds

```bash
# Build only the autonomy bringup package
colcon build --packages-select quadcopter_bringup

# Build perception package
colcon build --packages-select quadcopter_perception

# Build PX4 interface packages
colcon build --packages-select px4_msgs px4_ros_com

# Release build for performance (Raspberry Pi 5 deployment)

```

### 5.2 Rebuild After Interface Changes

When `px4_msgs` message definitions change, rebuild the interface package first, then everything that depends on it:

```bash
colcon build --packages-select px4_msgs --cmake-clean-cache
colcon build --symlink-install
```

### 5.3 Source the Workspace

```bash

```

Recommended `~/.bashrc` additions:

```bash
source /opt/ros/humble/setup.bash
source ~/path/to/gps-denied-vtol/software/src/install/setup.bash
```

```bash
colcon build --cmake-clean-cache   # rebuild CMake cache only
rm -rf build install log           # full clean
```

## 6. Running the System

### 6.1 MicroXRCE-DDS Agent (Required for PX4 <-> ROS 2)

PX4 and ROS 2 communicate over **uXRCE-DDS** (micro-ROS). The flight controller runs a micro XRCE-DDS *client* and the companion computer runs the **MicroXRCE-DDS Agent**, which exposes PX4 uORB topics on the ROS 2 graph as `/fmu/*` topics. Nothing works until this agent is running.

#### 6.1.1 Install

```bash
# Option A - prebuilt Debian package (simplest)
sudo apt install ros-humble-micro-ros-agent

# Option B - build from source (latest, useful on Raspberry Pi 5)
git clone https://github.com/eProsima/Micro-XRCE-DDS-Agent.git
cd Micro-XRCE-DDS-Agent && mkdir build && cd build
cmake ..
make
sudo make install
sudo ldconfig
```

Both produce the `MicroXRCEAgent` executable (and, if installed via the ROS package, the `micro-ros-agent` alias).

#### 6.1.2 Transports

| Transport | Use case                   | Command                                              |
| --------- | -------------------------- | ---------------------------------------------------- |
| UDP       | SITL simulation (loopback) | `MicroXRCEAgent udp4 -p 8888 -v`                     |
| Serial    | Kakute H7 over UART (TELEM2) | `MicroXRCEAgent serial --dev /dev/ttyAMA0 -b 921600` |
| Ethernet  | Pixhawk on the network     | `MicroXRCEAgent udp4 -p 2019 -r 2020`                |

#### 6.1.3 PX4-side configuration

- **Hardware (Kakute H7):** set `UXRCE_DDS_CFG` to **TELEM2** and `SER_TEL2_BAUD` to `921600` in QGroundControl, then reboot the flight controller.
- **SITL:** the PX4 SITL firmware starts its own uXRCE-DDS client on UDP port `8888`, so the agent must listen on that port. No extra config required.

#### 6.1.4 Verify

```bash
ros2 daemon stop && ros2 topic list | grep -E 'fmu|vehicle'
```

If no `/fmu/*` topics appear, the agent is not running, the client is not connected, or the transport/baud settings are wrong.

### 6.2 Inspect the ROS 2 Graph

```bash

ros2 topic list
ros2 topic echo /fmu/out/vehicle_attitude
```

### 6.5 Bringup - Simulation (SITL)

#### 6.5.1 One-launch method (recommended)

`quadcopter_bringup` ships `sitl_gz.launch.py`, which starts the
MicroXRCE-DDS agent, PX4 SITL (`gz_x500` in the selected world), and the
`ros_gz_bridge` (`/clock` + x500 pose/odometry) in one go. It uses the
system `gz` (Harmonic, 8.x) binary — not `ign` (6.x) — as required by PX4
main (`px4-rc.gzsim` enforces GZ >= 8.0.0).

```bash
cd software/src && source install/setup.bash

# Default: x500 in baylands + agent on UDP 8888 + bridge
ros2 launch quadcopter_bringup sitl_gz.launch.py

# Options
ros2 launch quadcopter_bringup sitl_gz.launch.py world:=forest
ros2 launch quadcopter_bringup sitl_gz.launch.py headless:=true
ros2 launch quadcopter_bringup sitl_gz.launch.py --show-args  # list all args
```

Then drive the drone from a second terminal:

```bash
cd software/src && source install/setup.bash
ros2 run quadcopter_bringup teleop
```

#### 6.5.2 PX4 shell prestep (failsafes + arm)

SITL has no GCS/RC, so disable the datalink-loss failsafe and arm from the
`pxh>` shell (in the PX4 SITL terminal). `teleop` also auto-arms via
`VehicleCommand`, so `commander arm` is only needed for manual bring-up:

```
pxh> param set NAV_DLL_ACT 0
pxh> param set COM_CBK_GCS_ACT 0
pxh> param save
pxh> commander arm
```

> `NAV_DLL_ACT 0` = GCS-loss action Disabled (verified in
> `commander_params.yaml`). `COM_CBK_GCS_ACT` is not a known param in PX4
> main — confirm with `param show COM_*`; you probably want
> `COM_DL_LOSS_T` (timeout) or `COM_OBL_ACT`/`COM_OBL_RC_ACT` (offboard-loss
> action) instead.

Verify the graph:

```bash
ros2 topic list | grep -E 'clock|model|fmu'
gz topic -l | grep -E 'x500|clock'  # raw Gazebo topics
```

#### 6.5.3 Manual method (three terminals)

```bash
# Terminal 1 - MicroXRCE-DDS agent over UDP loopback
MicroXRCEAgent udp4 -p 8888 -v

# Terminal 2 - PX4 SITL + Gazebo Harmonic (from the PX4-Autopilot source directory)
PX4_GZ_WORLD=baylands make px4_sitl gz_x500

# Terminal 3 - ROS 2 bridge + teleop node
cd software/src && source install/setup.bash
ros2 run ros_gz_bridge parameter_bridge \
  /clock@rosgraph_msgs/msg/Clock[ignition.msgs.Clock \
  /model/x500/odometry@nav_msgs/msg/Odometry[ignition.msgs.Odometry \
  /model/x500/pose@geometry_msgs/msg/PoseArray[ignition.msgs.Pose_V
ros2 run quadcopter_bringup teleop
```

### 6.6 Bringup - Hardware (Real Robot)

1. Power the airframe; confirm the Kakute H7 boots and the Raspberry Pi 5 links over UART.
2. Set `UXRCE_DDS_CFG` = TELEM2 and `SER_TEL2_BAUD` = 921600 in QGroundControl and reboot the flight controller.
3. Verify MAVLink telemetry in QGroundControl.
4. Start the agent and the ROS 2 node:

```bash
MicroXRCEAgent serial --dev /dev/ttyAMA0 -b 921600

cd software/src && source install/setup.bash
ros2 run quadcopter_bringup teleop
```

### 6.7 Controlling the Quadcopter (Keyboard Teleop)

`quadcopter_bringup` ships a keyboard teleop node that drives the PX4 velocity setpoints in Offboard mode over uXRCE-DDS:

```bash
ros2 run quadcopter_bringup teleop
```

| Key      | Action                    |
| -------- | ------------------------- |
| `w`      | Move forward (+X)         |
| `s`      | Move back (-X)            |
| `a`      | Move left (+Y)            |
| `d`      | Move right (-Y)           |
| `r`      | Move up (-Z, NED)         |
| `f`      | Move down (+Z, NED)       |
| `x`      | Stop / hover in place     |
| `q`      | Increase max speed by 10% |
| `z`      | Decrease max speed by 10% |
| `Ctrl+C` | Exit safely               |

The node publishes `OffboardControlMode` and `TrajectorySetpoint` at 20 Hz, switches PX4 to **Offboard** mode after ~15 setpoints, and sends the **arm** command after ~30. Always keep the RC transmitter in an override-capable mode and test in SITL before hardware.

## 8. Development Workflow

### 8.1 Conventions

- **ROS 2 (Humble):** `ament_python` / `ament_cmake` packages with `package.xml` (format 3).
- **Python:** PEP 8, enforced by `flake8` / `pep257` test suites. Do not disable these checks.
- **C++:** C++17 (see `.vscode/c_cpp_properties.json`), enforced by `ament_lint_auto`.
- **Messages:** add any new uORB-facing types to `px4_msgs`; keep definitions aligned with PX4.

### 8.2 Adding a New Node

1. Create the node under `software/src/quadcopter_bringup/quadcopter_bringup/` or `software/src/quadcopter_perception/quadcopter_perception/`.
2. Register executables in `setup.py` (`entry_points.console_scripts`).
3. Add launch files under `launch/` and list them in the `data_files` of `setup.py`.
4. Rebuild and test:

```bash
cd software/src && colcon build --packages-select quadcopter_bringup --symlink-install
colcon test --packages-select quadcopter_bringup
```

### 8.3 Code Review Checklist

- [ ] Dependencies declared in `package.xml`.
- [ ] `flake8` and `pep257` clean.
- [ ] No hardcoded paths/ports - use launch parameters.
- [ ] Topics/services namespaced (e.g. `/fmu/in/`, `/perception/`, `/slam/`).
- [ ] Graceful shutdown on `SIGINT`; no orphaned agents.
- [ ] Log messages include node name and severity level.

### 8.4 Git Guidelines

- Branch per feature: `git checkout -b feature/<name>`.
- Conventional commit messages (e.g. `feat:`, `fix:`).
- Rebase onto `main` before opening a Pull Request.
- Never commit `build/`, `install/`, `log/`, or `.vscode/` artifacts.

## 9. Troubleshooting

| Symptom                              | Likely Cause                            | Resolution                                                        |
| ------------------------------------ | --------------------------------------- | ----------------------------------------------------------------- |
| No `/fmu/*` topics                   | MicroXRCE-Agent not running             | Start the agent (Section 6.1); verify with `ros2 topic list`.      |
| Agent starts but no data in SITL     | Wrong UDP port                         | PX4 SITL client uses port `8888`; run `MicroXRCEAgent udp4 -p 8888`. |
| Agent disconnects on hardware        | Wrong port / baud rate                  | Check TELEM2 wiring, set `-b 921600`, and confirm `UXRCE_DDS_CFG` = TELEM2 in QGC. |
| `ros2 run` says package not found    | Workspace not sourced                   | `source install/setup.bash` after `colcon build`.                  |
| `ros2 run quadcopter_bringup teleop` not found | Old build / entry point not installed | `colcon build --packages-select quadcopter_bringup --symlink-install`. |
| Lint test failures                   | Style violations                        | Run `colcon test --packages-select quadcopter_bringup` and fix reported issues. |
| SITL model does not start            | Gazebo / PX4 environment not sourced    | Source the PX4 `Tools/setup_gazebo.bash` and `~/PX4-Autopilot` env. |
| Teleop does not arm                  | Not in Offboard / safety checks fail    | Confirm mode switch + arm log lines; check QGC arming checks; keep RC override available. |
| High CPU/temperature on Pi 5         | Clock throttling                        | Check `vcgencmd measure_temp`; cap detection frame rate.           |

## 10. Safety & Operational Guidelines

- Always operate with propellers removed during bringup, calibration, and offboard development.
- Arm the vehicle only after the flight controller passes preflight checks in QGroundControl and an RC failsafe is configured.
- Keep the RC transmitter in a **manual-override-capable** flight mode and test failsafes (RTL, low battery) in SITL before hardware.
- Run offboard tests in SITL first; verify the kill-switch / disarming behavior before real-robot trials.
- Fly within line of sight, in a cleared area, with a spotter, and never over people.
- Secure the battery and confirm secure propeller retention before flight.
- **GPS-denied specific:** Verify visual-inertial odometry quality before relying on offboard control; have a dead-reckoning fallback mode tested.
